## Persona
Veteran system integrator (20 years, Ignition Gold, has architected multi-site Ignition + MES systems); judges on accuracy, real-world depth, and whether a student could walk into an interview.

## What works
- **arch-patterns**: "What forces me off one box?" framing and the "When to split, and when not to" section. A senior integrator would say the same thing to a customer. The pitfalls list is honest.
- **ign-udts**: the definition-vs-instance split, overridden setpoints ("tank 7 must alarm at 80") and the "Bad_NotFound after a controller edit" example teach the failure mode that actually happens on site. The Motor worked example is concrete.
- **plc-best-practices**: the one-writer-per-bit rung trace (quiz 2), "PLC owns control alarms, SCADA owns presentation", and the 12-item code review checklist are the habits I enforce on other people's code.
- **int-capstone**: decision-log format with "alternatives / why not" is the right artifact. The arithmetic checks out: 150 msg/s x 120 B = 18 KB/s = 144 kbit/s, and 99.9% allows about 8.8 h/yr.
- **persp-library**: one tagPath parameter with "derive, do not pass", and semver rules for UDT contract changes. This is how a library should be run.
- **Structure**: every {{term:...}} reference and keyTerm in the six lessons resolves to a glossary id, and every {{lesson:...}} target exists.

## Problems
**[severity: high] [area: accuracy]** ign-udts (Motor example and quiz), plc-best-practices ("Cmd/Sts/Cfg" table), persp-library (faceplate bindings and rename quiz) — Three different member naming conventions for the same Motor UDT. ign-udts uses `Cmd_Start`, `Sts_Running`, `Sts_Fault`. plc-best-practices uses `Cmd.Start`, `Sts.Running`, `Cfg.HighLimit`. persp-library binds `Status/Running`, `Cmd/Start`, `Cfg/Description`, `Status/Permissives`. A student who builds the UDT from one lesson and the faceplate from another gets exactly the Bad_NotFound failure ign-udts warns about. Fix: pick one convention (the PLC-side Cmd/Sts/Cfg, one separator), state it once in int-naming, and rewrite the examples, bindings and quizzes in all three lessons to match.

**[severity: high] [area: accuracy]** arch-patterns, Pattern 2 body ("sessions can land on any front-end ... stickiness should be long") and "Why scale-out's front-end must be stateless" (quiz 4: "A load balancer may send a user to any front-end") — The mechanism is backwards. Perspective sessions live in memory on the gateway that owns them, which is why the load balancer must pin a client to one front-end (session affinity). Stateless still matters for shared config and failover, but the lesson's stated reason is wrong. Fix: explain session affinity, say what a front-end failure does to its sessions (clients reconnect and state is lost), and check against the IA scale-out guide before publishing.

**[severity: high] [area: accuracy]** int-capstone, D4 ("The topic hierarchy follows ISA-95 naming: `meridian/<site>/<area>/<line>/<equipment>/...`" under the Sparkplug B sentence) — Sparkplug B has a fixed topic namespace (`spBv1.0/<group_id>/<message_type>/<edge_node_id>[/<device_id>]`). A custom ISA-95 path only exists for plain MQTT/UNS topics. An integrator reviewing this would stop reading. Fix: split it into two rules, one for Sparkplug (group and node IDs map to site and line) and one for non-Sparkplug UNS topics, and make it match what mes-uns and arch-mqtt teach.

**[severity: high] [area: accuracy]** int-capstone, R4 and D5/D7 ("Chicago HMI/history 99.9 percent"; D7 makes only the gateway pair redundant; D5 puts "its own SQL database server in Level 3" with no HA) — The availability target covers history, but the database is a single point of failure in the design. arch-patterns' own pitfall says "Forgetting the database is a single point of failure in every one of these patterns." Fix: add database HA to D7 (or the DB cost to the decision), or restate R4 for the gateway only and show the chained availability calculation. Link db-operations for the HA choice.

**[severity: high] [area: accuracy]** arch-patterns, "Choosing a pattern" table ("under about 100k tags, under about 50 clients") vs. prose ("about 100 clients, 100 devices and 150,000 tags") and the opener "Ignition licenses by server, not by tag or client count." — Two different thresholds for the same decision, and the opener ignores that Perspective sessions and Vision clients are licensed separately, which is the reason client count matters. Fix: one threshold set, cited to a dated IA source, and a corrected licensing sentence that says to check current session/client licensing with IA.

**[severity: high] [area: content]** mes-sepasoft, "What a typical implementation looks like" step 4 and "Batch Procedure" paragraph — This reads as a product brochure. The one line about the hardest work ("Map PLC tags for counts, states and fault codes to the model. Fix the data first") is never shown: no count tag or good/bad count pattern, no state-tag-to-mode mapping, no reason-code flow, no sample tree in the Designer. The Batch Procedure sentences ("suits dozens of data points per phase"; "positions its recipes as including the workflow, operator steps and approvals") are vague paraphrase. The lesson also quotes version numbers from memory (4.83.x, 3.81.11) while its own pitfall warns against that. Fix: add a worked Line 3 example (tag list, mode list, one downtime event from PLC state change to Pareto row), and link each version claim to the Sepasoft page at the point of use.

**[severity: med] [area: accuracy]** plc-best-practices, "Tags and members: PascalCase with underscores only as area separators, e.g. `P101_Pump`, `Area10_Mixing`" — The examples use underscores between equipment tag and type (`P101_Pump`), not only for area. Fix: state the rule exactly (for example, underscore between equipment tag and descriptor, and between area and name) and use the same rule in the capstone's `UDT_Motor` examples.

**[severity: med] [area: content]** plc-best-practices, "Libraries" and "Source control" sections — "Commercial tools (version-control and change-management products for controllers)" names nothing. A hiring manager will expect FactoryTalk AssetCentre to be named. The L5X advice also omits the warning that importing an L5X into a live project can overwrite same-named items, which is how controllers get damaged by a "restore". Fix: name the Rockwell tool, add the import-conflict warning, and add a lab exercise that round-trips a routine through L5X.

**[severity: med] [area: content]** ign-udts, "Putting behaviour in the definition" and the "In 8.1" box — The lesson never mentions tag groups or scan rate per UDT member. Its own example (40 motors x 9 live tags, one of which is historized) is exactly where polling load and tag group choice decide whether a server is healthy. The 8.1 note ("8.x UDTs inherit from a parent type through the definition, not through copying") says nothing concrete about what "copying" means. Fix: add a short section on tag groups and scan classes per member with the 40-motor sizing, and replace the 8.1 note with one specific difference or delete it.

**[severity: med] [area: accuracy]** persp-library, "Selecting the right faceplate by type" (`library.faceplates.openFaceplate` calling `system.tag.getConfiguration(tagPath, False)[0]['typeId']` on every click) — The lesson never says which script scope the library runs in, and Perspective client scope may not be able to make that call. Even where it works, a tag-config query on every faceplate open is avoidable. Fix: state the scope, verify the call works from it, and either cache the type map or pass the UDT type from the symbol. Treat this as something to verify, not a confirmed bug.

## Missing
- A hands-on Ignition build lab. The simulator has 25 ladder challenges, and none of these six lessons ends in something you build: a Motor UDT with the same members as a Logix UDT, a simulated device feeding it, a faceplate bound to it. A hiring manager tests that, not recall.
- A lesson on Ignition licensing and sizing (Perspective session vs. Vision client, Edge limits, module licensing). It is only touched in arch-patterns, and the capstone depends on it.
- Time synchronization (NTP/PTP, controller vs. server timestamps, sequence-of-events). It is absent from the curriculum index. Alarm journals and historian data in the capstone are meaningless without it.
- Logix driver addressing and connection tuning in Ignition (CIP connections, RPI, bad-quality triage on the Allen-Bradley driver). ign-devices is generic, and this is the most common day-to-day failure in a Logix shop.
- A career and portfolio lesson that says what to build to be hireable. int-career is 10 minutes at level 1 at the end of T9 (from the index; I did not read it, so verify), which is thin for a track whose point is employment.

## One-line verdict
Sound architecture judgment and good decision frames, but the Ignition and MES lessons would not make a hire yet: they contradict each other on naming, one Sparkplug and one session-affinity explanation are wrong, and nothing has the student build anything.
